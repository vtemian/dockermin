# Decision: v1.1 GRPO retry (v2 adapter) headline result and how we almost missed it

**Date:** 2026-06-02
**Status:** Final

## TL;DR

`vtemian/dockermin-qwen7b-lora-v2/step_250` evaluated at `T=0.2` is the **winning
checkpoint** for the project's headline metric (mean size reduction conditional on
test pass). It ties the untrained baseline on pass rate (56.8 %) but **more than
doubles the size reduction quality** (75.3 % vs. 32.1 %), beating every other
baseline in the leaderboard — including Sonnet zero-shot.

## Context

The v1 (first GRPO attempt) result, captured in the project's earlier
documentation, was a null: dockermin v1 ≈ qwen_zs at 56.8 % pass and roughly the
same reduction. That triggered the v1.1 retry plan (`docs/plans/2026-05-28-grpo-v1-retry.md`)
with four fixes: reward magnitudes, batch tuning, zero-advantage filter, and
the pad-the-Dockerfile cap.

Training completed on pod #4 at step 250. The training-time **rolling pass rate
climbed 25 % → 80 %** over the 250 steps. On first eval (`step_250 @ T=0.2`) the
holdout pass rate landed at **56.8 %** — identical to v1 and qwen_zs. The
initial read was that v2 was another null result and that the NEGATIVE_RESULT.md
trigger had fired.

## The investigation that overturned the null verdict

When Vlad pushed back and asked for a deeper analysis, four parallel subagent
investigations ran (about 45 minutes wall-clock total):

### Agent A — train/eval prompt and infrastructure mismatch

Found nine candidate gaps; two ranked high:

1. **Sampling mismatch** — training samples at T ≈ 1.0 with `max_completion_tokens = 2048`
   in the orchestrator config; eval was hard-coded to `temperature = 0.2,
   do_sample = True, max_new_tokens = 1024`. Predicted: closing the gap would
   raise eval pass rate substantially.
2. **Inference engine drift** — training runs vLLM; eval runs HF transformers
   + PEFT. LoRA-sensitive numerical drift, especially at non-greedy sampling.

Lower-impact gaps found: a `.strip()` applied to the user dockerfile in eval
but not training (`src/dockermin/reward/prompts.py:37` vs.
`prime_env/dockermin_env/dockermin_env.py:23`), and a `build_timeout_s = 300`
during training vs. `600` during eval (would inflate eval pass rate, not
suppress it — wrong direction).

### Agent B — checkpoint-selection (mode collapse) analysis

Computed the L2 norm of the LoRA `lora_B` matrices across step_25 → step_250
shards on HF. Found weights still drifting at step_250 (per-step `‖ΔW‖` had
halved from early training but was not zero), and successive deltas were
moderately coherent (cosine ≈ 0.5). Concluded **step_250 is NOT mode-collapsed
in the trivial sense**. Recommended eval-ing step_100 as a tie-break.

### Agent C — Devil's-advocate audit (reward-hack / trivial-pass detection)

Pulled the v2 eval results and bucketed the 21 passes by reduction magnitude:

| Bucket | Definition | Count |
|---|---|---:|
| Trivial pass | ≤ 1 % reduction | 0 |
| Modest | 1–10 % | 0 |
| Real | 10–30 % | 0 |
| Big | > 30 % | 21 |

Min reduction on a pass: 55.3 %. Median: 73.5 %. Max: 95.9 %. None of the 21
passes were echo-the-input.

**This was the result-overturning finding.** The 56.8 % pass rate was indeed
identical to qwen_zs, but the *quality* of those passes had jumped. The mean
reduction comparison (using the median variant baseline size for each
source URL):

- qwen_zs (untrained): pass rate 56.8 %, mean reduction 60.6 %, 4.26 GB saved
- v2 step_250 @ T=0.2: pass rate 56.8 %, **mean reduction 85.7 %, 7.05 GB saved**

The canonical `scripts/leaderboard.py` (which uses an arbitrary single
baseline_size per source URL rather than the median, so the absolute reduction
numbers are slightly different from the median-variant analysis) confirms the
same story: 75.3 % vs. 32.1 %.

### Agent D — metric-definition forensics

Verified the "80 % training rolling pass rate" was a strict lower bound on
`test_passes = True`. The reward ladder enforces `max(non-pass) = 0.45 < 0.5
= min(pass-floor)` (gates.py:19 comment), so every rollout scoring ≥ 0.5 is a
real pass. The training pass rate was not inflated by counting test-fail rungs
as passes.

## Verification: the three follow-up evals

After Agent C overturned the null reading, three additional cells of the
{checkpoint × temperature} matrix were filled in (PR #5 added the
`--temperature` and `--max-new-tokens` flags plus `EvalEntry.rewrite_dockerfile`
so the eval is now reproducible).

| Cell | Pass rate | Mean reduction \| pass | What it told us |
|---|---:|---:|---|
| v2 s250 @ T=0.2 | 56.8 % | 85.7 % (75.3 % canonical) | the headline |
| v2 s100 @ T=1.0 | 45.9 % | 66.5 % (40.1 % canonical) | step_100 outperformed step_250 at T=1.0 (Agent B partially confirmed) |
| v2 s250 @ T=1.0 | 35.1 % | 77.2 % (37.3 % canonical) | T=1.0 *hurts* eval pass rate; Agent A's sampling-mismatch hypothesis is rejected |
| v2 s100 @ T=0.2 | 54.1 % | 60.5 % (32.7 % canonical) | step_100 ≈ qwen_zs on every axis — the late-training portion is doing real work |

## What this means

1. **The technique works.** GRPO on parse+build+test rewards produced a model
   that shrinks dockerfiles 2.3× more aggressively than the base on the same
   set of passing prompts, on a held-out test set.
2. **Pass rate is the wrong yardstick alone.** The pass rate of v2 == qwen_zs,
   so a pass-rate-only comparison reads as a null. The project's actual
   headline metric — `Mean reduction conditional on test pass` — is what the
   leaderboard sorts on, and is where the win lives.
3. **The training pass-rate climb (25 % → 80 %) was real but did not transfer.**
   On the holdout the model handles the same 56.8 % of cases it always did; the
   training distribution presumably differed enough from the holdout that the
   "more cases passed" gains overfit. **What did transfer** was the size-reduction
   policy: on the cases that pass, the model now shrinks much harder.
4. **Sampling at T = 0.2 is the right eval setting.** Empirically, matching the
   GRPO training T ≈ 1.0 *lowered* pass rate by 22 points on step_250 and 9
   points on step_100. The "T mismatch causes the train/eval gap" hypothesis is
   falsified.
5. **step_250 is the right checkpoint to ship.** step_100 is statistically
   indistinguishable from qwen_zs at T = 0.2 (54.1 % vs 56.8 %, 32.7 % vs 32.1 %
   reduction). The size-reduction policy was learned in the second half of
   training.

## What I'd do differently if running v3

1. **Switch reward gates from `docker buildx` to plain `docker build`.** The
   buildx builder cache is the disk-fill amplifier we spent multiple pods
   diagnosing.
2. **Match the holdout distribution in training.** v2's training set was 108
   examples covering 28 unique bases; the 37-example holdout has 9 unique
   source URLs. A wider training set would test whether the pass-rate ceiling
   moves.
3. **Persist `wandb` outside the pod from step 1.** The training rollouts JSONL
   was on the pod's disk and lost when pod #4 was terminated; the
   `hf_pusher.sh` only pushed adapter shards, not rollouts. Future runs should
   push rollouts too so a post-mortem can re-bucket reward by category.
4. **Eval multiple checkpoints by default.** Spending one extra $2 eval on
   step_100 was the bow on the result. Make it part of the `eval_unattended.sh`
   recipe.
